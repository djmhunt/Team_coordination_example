# Demo Guide: Presenting GitHub to Non-Technical Colleagues

This guide helps you demonstrate this repository and GitHub's collaboration features to non-technical curriculum team members.

## Pre-Demo Setup (15 minutes)

### 1. Enable GitHub Features
- **Go to Settings** → Features
- ✓ Enable **Wikis**
- ✓ Enable **Discussions**
- ✓ Enable **Issues** (should already be on)
- ✓ Enable **Projects**

### 2. Create a Sample Project Board
1. Go to **Projects** tab → **New project**
2. Name it "Curriculum Development Pipeline"
3. Choose "Board" view
4. Create columns:
   - 📋 Proposed
   - 👀 In Review
   - ✅ Approved
   - 🚀 Implemented

### 3. Create a Sample Wiki Page
1. Go to **Wiki** tab → **Create the first page**
2. Title it "Home"
3. Paste this content:
   ```markdown
   # Curriculum Team Wiki
   
   Welcome to our knowledge base!
   
   ## Quick Links
   - [[Course Development Guidelines]]
   - [[Meeting Notes]]
   - [[Resources]]
   
   This wiki is where we maintain our living documentation.
   ```

### 4. Optional: Create a Sample Issue
1. Go to **Issues** → **New issue**
2. Choose "Course Proposal" template
3. Fill it in with a sample course idea
4. Submit it (you can close it after the demo)

## Demo Script (20-30 minutes)

### Opening (2 minutes)

**What to say:**
> "I want to show you how we can use GitHub to better coordinate our curriculum work. GitHub isn't just for programmers—it's a powerful collaboration platform that can help us work together asynchronously on proposals, policies, and sharing teaching practices."

**Show:** The main README.md file

### Part 1: Issues - Tracking Proposals & Tasks (7 minutes)

**What to say:**
> "Think of Issues like a smart combination of email threads and task lists. Each issue tracks one proposal, discussion, or action item."

**Demonstrate:**
1. Click **Issues** tab
2. Click **New issue**
3. Show the template choices
4. Click "Course Proposal"

**Point out:**
- Pre-filled structure (they don't start from scratch)
- Labels that help organize items
- Comments section for discussion
- @mentions to bring in specific people
- Linking to other issues with #number

**What to say:**
> "Instead of email chains that get lost, all discussion about a proposal stays in one place. Everyone can see it, and GitHub notifies the right people."

### Part 2: Projects - Visual Workflow (5 minutes)

**What to say:**
> "Projects give us a visual way to see where everything stands—like a digital bulletin board."

**Demonstrate:**
1. Go to **Projects** tab
2. Open your sample project
3. Show how items move between columns
4. Create a draft item: "Review assessment policy"
5. Drag it from "Proposed" to "In Review"

**Point out:**
- Visual progress tracking
- Multiple views (Board, Table, Roadmap)
- Easy to see what's stuck or moving forward
- Links to full discussions in Issues

### Part 3: Wiki - Knowledge Base (5 minutes)

**What to say:**
> "The Wiki is our institutional memory. It's where we keep documentation that changes over time—policies, guidelines, best practices."

**Demonstrate:**
1. Go to **Wiki** tab
2. Show the home page
3. Click **Edit** to show how easy it is to update
4. Create a new page called "Teaching Resources"

**Point out:**
- Everyone can edit (it's collaborative)
- Version history (can see who changed what)
- Searchable (no more lost documents)
- Links between pages for easy navigation

**What to say:**
> "Unlike a shared drive where files get outdated, the wiki is always current because anyone can update it."

### Part 4: Discussions - Open Conversations (4 minutes)

**What to say:**
> "Discussions are for conversations that don't need task tracking—brainstorming, Q&A, sharing resources."

**Demonstrate:**
1. Go to **Discussions** tab
2. Show how to start a new discussion
3. Show categories (General, Ideas, Q&A)
4. Point out reactions and threaded comments

**Point out:**
- Less formal than Issues
- Categories keep things organized
- Can mark answers (for Q&A)
- Good for community building

### Part 5: Documents - Templates & Examples (5 minutes)

**What to say:**
> "We've set up templates and examples to make it easy to get started."

**Demonstrate:**
1. Click **Code** tab
2. Navigate to `docs/templates/`
3. Open `course-proposal.md`
4. Show the comprehensive structure
5. Navigate to `docs/proposals/`
6. Open `data-literacy-course.md`
7. Show how it uses the template

**Point out:**
- Templates ensure consistency
- Examples show what good looks like
- Easy to reference: just link to the file path
- Version control tracks all changes

### Part 6: Getting Started (2 minutes)

**What to say:**
> "Getting started is easy. Let me show you the Quick Start Guide."

**Demonstrate:**
1. Open `docs/QUICK_START.md`
2. Walk through the 3 steps
3. Show the "What to Do Next" section

**Provide:**
- Link to the repository
- Link to `docs/QUICK_START.md`
- Offer to help with first issue or discussion

### Closing Q&A (3-5 minutes)

**Common Questions & Answers:**

**Q: "Do I need to know how to code?"**
A: "Not at all! Everything we showed uses GitHub's web interface—just point and click, like any website."

**Q: "What if I make a mistake?"**
A: "Everything has version history, so mistakes can be undone. Plus, you can preview before saving."

**Q: "How do I get notified about updates?"**
A: "Click 'Watch' at the top of the repository. You'll get email notifications for new issues and discussions."

**Q: "Can we try this without disrupting our current workflow?"**
A: "Absolutely! Start with one thing—maybe sharing good practices or one proposal. No need to change everything at once."

**Q: "What if someone needs help?"**
A: "There's a comprehensive guide at `docs/GITHUB_GUIDE.md`, plus you can start a Discussion to ask questions."

## Follow-Up Actions

### Immediately After Demo
1. Send email with:
   - Link to repository
   - Link to Quick Start guide
   - Invitation to "Watch" the repository
   - Your contact info for questions

2. Create a welcome Discussion post:
   > "Welcome to our new collaboration space! Feel free to explore and ask questions here."

### First Week
1. Post a sample issue using one of your templates
2. Add a page to the wiki
3. Encourage one person to share a good practice
4. Be very responsive to questions

### First Month
1. Have a feedback session
2. Adjust templates based on what people actually need
3. Celebrate early wins
4. Create more wiki pages based on what gets asked

## Tips for Success

### Do:
- ✅ Start small (one feature at a time)
- ✅ Use real examples from your actual work
- ✅ Be patient with questions
- ✅ Celebrate people's first contributions
- ✅ Keep it informal and welcoming
- ✅ Emphasize "everything is fixable"

### Don't:
- ❌ Overwhelm with too much at once
- ❌ Use technical jargon
- ❌ Make people feel they need to learn everything immediately
- ❌ Criticize people's early attempts
- ❌ Force everyone to use every feature
- ❌ Compare to programming workflows

## Adaptation Ideas

### For Different Audiences

**Senior Leaders (10 minutes)**
- Focus on transparency and accountability
- Show project boards for tracking progress
- Emphasize searchability and knowledge retention
- Demonstrate how decisions are documented

**Faculty Members (20 minutes)**
- Focus on sharing teaching practices
- Show course proposal workflow
- Emphasize how it reduces email overload
- Demonstrate collaborative document editing

**Committee Members (30 minutes)**
- Show complete workflow from proposal to approval
- Demonstrate how to review and provide feedback
- Show meeting notes and action item tracking
- Practice using issue templates

**Student Representatives (15 minutes)**
- Focus on transparency (they can see what's being discussed)
- Show how to provide input on proposals
- Emphasize that anyone can contribute
- Keep it informal and welcoming

## Measuring Success

After 1-3 months, look for:
- Number of active participants
- Issues/discussions created
- Wiki pages maintained
- Positive feedback about the workflow
- Reduction in "lost" emails or decisions
- Increased transparency in decision-making

## Troubleshooting Demo Issues

**If the internet is slow:**
- Have screenshots prepared as backup
- Download the repository and show files locally
- Focus on one feature instead of all

**If people seem confused:**
- Slow down
- Let them try clicking around
- Focus on just Issues first
- Schedule follow-up 1-on-1 sessions

**If people resist:**
- Acknowledge their concerns
- Start with volunteers only
- Run a small pilot first
- Emphasize it's complementary, not replacement

**If technical issues occur:**
- Have a backup plan (screenshots, local files)
- Acknowledge the issue with humor
- Focus on the concepts, not the clicks
- Offer to do individual walkthroughs later
